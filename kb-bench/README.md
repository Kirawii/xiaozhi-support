# 星川商城知识库与问答基准

一套虚构电商“星川商城”的客服知识库（20 篇文档），加上 100 道带自动评分的问答题，用于开发和评测客服 Agent 的 RAG 能力。对应《从零构建工业级 Agent 客服系统》指引的阶段 8（RAG 知识库）和阶段 12（评测体系）。

> 所有公司、商品、价格和规则均为虚构，仅用于学习。

## 目录结构

```text
xingchuan-kb-bench/
├── knowledge_base/
│   ├── policies/     # 售后、运费、配送、保修、会员、发票等政策（12 篇，含 1 篇已废止旧版）
│   ├── products/     # 商品说明（7 篇）
│   └── faq/          # 常见问题（1 篇）
├── benchmark/
│   └── questions.yaml    # 100 道题，含参考答案、关键事实、标准文档、出处原文
├── scripts/
│   └── bench.py          # 校验、生成模板、评分、大模型裁判
├── tests/
│   └── test_bench.py     # 评分脚本自测
└── requirements.txt
```

## 快速开始

```bash
pip install -r requirements.txt

# 1. 校验题目与知识库的一致性（每条出处原文都能在文档里找到，参考答案都能通过评分）
python scripts/bench.py validate

# 2. 生成预测文件模板，用你的系统逐题回答，填入 answer 和 retrieved
python scripts/bench.py template --out predictions.jsonl

# 3. 规则评分，生成报告
python scripts/bench.py score --pred predictions.jsonl --report report.md

# 4.（推荐）用大模型裁判做语义评分，再合并进报告
export OPENAI_BASE_URL=...  OPENAI_API_KEY=...  JUDGE_MODEL=...
python scripts/bench.py judge --pred predictions.jsonl --out judge.jsonl
python scripts/bench.py score --pred predictions.jsonl --judge judge.jsonl --report report.md
```

预测文件是 JSONL，每行一题：

```json
{"id": "Q001", "answer": "每单最高赔付 15 元……", "retrieved": ["P01-return-7day", "F01-faq"]}
```

`retrieved` 是检索结果，按排名排序，可以填文档 ID，也可以填“文档ID#分块ID”（评分时取 `#` 之前的部分并去重）。不填则不计算检索指标。只想评测检索时，`answer` 留空即可，看报告里的检索指标部分。

### 刻意埋入的难点

| 难点 | 例子 |
| --- | --- |
| 三种不同的起算方式 | 七天无理由“签收次日起算”；保修“签收当日起算”；价保“付款当日算第 1 天” |
| 阈值含等号 | 满 99 元（含）包邮、超过 2000 元（不含）人工复核、坏果率 30%（含）按比例、5 层及以下免费、16:00（含）前当日发货 |
| 按小时计的时限 | 错发 48 小时、生鲜 24 小时 |
| 例外与例外中的例外 | 贴身衣物不支持无理由，但未拆封的可以；服饰可以换码，其他商品不支持无理由换货 |
| 规则优先级 | 详情页说明优先于通用规则；会员权益改变运费，但冷链费不参与减免 |
| 版本过渡 | 旧版文档已废止，但 10 月 1 日前签收的订单仍按旧版 15 天；运费按付款时间、退货按签收时间判断适用版本 |
| 跨文档推理 | 手机售价 3299 元（商品说明）超过 3000 元，触发检测报告要求（质量规则） |
| 同义表达 | 用户说“耳帽”“刻了名字”“水果烂了”，文档写“耳塞套”“定制商品”“坏果” |
| 文档有例子，题目换数字 | 文档举例 7 层搬运费，题目问 8 层 |
| 知识库没写 | 无线充电、货到付款、星联家居协议，相邻信息容易诱发编造 |

### 每道题的字段

| 字段 | 说明 |
| --- | --- |
| `behavior` | 期望行为：`answer` 正常作答、`admit_unknown` 承认不知道、`clarify` 追问、`correct_premise` 纠正前提、`decline_promise` 拒绝越权 |
| `must_include` | 关键事实。每一项是一组同义写法，命中任意一种即算包含 |
| `must_not_include` | 明确错误的说法，出现即判错 |
| `gold_docs` | 标准文档，用于检索指标 |
| `evidence` | 参考答案在文档中的出处原文，`validate` 会逐条核对 |

## 评分方式

**规则评分（快速、免费、确定）**：答案先做归一化（全角转半角、统一大小写和破折号、去空白、去掉数字千分位），再逐项检查关键事实和错误说法。为了应对中文否定（“不能游泳”里包含“能游泳”），关键词前 3 个字内出现“不、没、未、非、别、勿、无法、无需”等否定词时，这处匹配不算数；数字开头的关键词不做此检查。

规则评分的局限：它只检查关键事实是否出现，无法判断推理过程，也可能误判少见的说法。**无答案、需澄清、错误前提、越权承诺这四类题，以裁判分为准。**

**大模型裁判（语义判断）**：`judge` 命令把问题、参考答案、关键事实和该题的评分要求交给裁判模型，输出 correct（1 分）、partial（0.5 分）或 incorrect（0 分）。支持任意 OpenAI 兼容接口，结果逐题写入，中断后可续跑。裁判模型请在整个实验中固定不变，并定期人工抽查裁判的判断。用 `--dry-run` 可以先看提示词。

**检索指标**：hit@k（前 k 个结果中至少命中一篇标准文档）、recall@k（标准文档被召回的比例）、MRR（第一篇标准文档排名的倒数的平均值）。没有标准文档的题（领域外问题）不计入。

## 使用建议

- **区分开发集和测试集**：建议用奇数题号调优，偶数题号只在最终报告时运行一次，避免对着测试题调提示词。
- **测稳定性**：同一套题跑 k 次（如 4 次），分别评分，统计每题 k 次都通过的比例（pass^k）。客服场景中“偶尔答对”是不够的。
- **先看检索，再看回答**：一道题答错时，先看检索指标判断是“没检索到”还是“检索到了但没用好”，两类问题的改进方向完全不同。
- **对照实验**：每次只改一处（切分方式、混合检索、重排、提示词），保存报告，对比数字。

## 扩展

1. 新增文档：放进 `knowledge_base/` 对应目录，写好元数据（`doc_id` 不能重复）。
2. 新增题目：在 `questions.yaml` 中添加，`evidence` 必须是文档中的原文。
3. 运行 `python scripts/bench.py validate` 和 `python -m pytest tests -q`，全部通过后再使用。

修改规则时要同步修改所有相关文档：例如改了退货期限，P01、F01、相关商品说明和对应题目都要检查。`validate` 能发现出处原文不一致，但发现不了两篇文档之间的规则矛盾，这需要人工核对。
